# Questions for James — EFS core contracts

Product choices the design (`docs/DESIGN.md` §21) leaves to the founder, each with the engineer's recommendation. Engineering choices are **not** listed here: §20 of the design records them with the alternative rejected and why, and C1 measurements resolve the rest by pre-stated rules.

How these map to earlier question ids: the initialization plan's D1 (build identity = compiled bytes) is applied in the repository (`docs/BUILD-IDENTITY.md`); D2 (all Types described, permissionless) is the design's §9; D3a/D3b are the S4 import lane and the S2b ERC-1271 lane; D4 (branch protection) is a repository-settings item outside this list; D5 is Q18; D6 and the naming note's N1/N2 are Q7; N3 (alias-on-rename default) and N4 (`~efs` reservation) are client-side policy and the `files-name/2` rule respectively and stay open in the naming note.

**Before S1 starts:** Q15 (who implements and who owns the M1 integration). **Before the first persistent Realm (any lasting deployment):** Q1, Q2, Q13, Q18, Q22, Q39, Q48, Q49, Q50, Q51 and Q53 (Q53 makes the three Topics Type ids final; Q52's build step must land before any freeze). **Before S2 freezes the `Intent` typehash:** Q5, Q6. **Before S3:** Q16, Q32. **Before S5:** Q3, Q10, Q27, Q33. Everything else can wait for the checkpoint that measures it.

## The questions (design §21)

1. **Structural `ruleId`** — codehash named in the descriptor (this design) or a grammar-profile commitment? One-way door closing at the first grade-1/2 registration on a persistent Realm (before S3). *Recommend codehash.*
2. **Signing domain** — chain- and deployment-bound EIP-712 with import as the only portability path. *Recommend bind.*
3. **Freeze end state** — (A) one-way burn; (B) append-only steward for replayed generations and codec/verifier additions; (C) immutable code without proxies at S5. *Recommend A for testnets; decide B/C before S5.*
4. **Supported inline body maximum under repricing** — 8,192 B (≈ 28.2M state gas, reservoir-only) or ≈ 4 KiB inline with a blob carrier above. *Recommend: measure at C1, publish in `limits`, keep the seam.*
5. **Witness retention** — hash + log by default; must import-eligible plans use `SignatureStore` retention (otherwise their 1271 authorship is `UNKNOWN` for portability)? *Recommend: default hash + log; state retention required for import.*
6. **Declaration signature profile** — EIP-712 EOA declarations at launch; ERC-1271 creators later. *Recommend yes.*
7. **Names N1/N2** — `files-name/2` as the only Name Type; NFC and case policy in the client. *Recommend yes.*
8. **Controller-owner change** — an activation (this design) or a recorded-only transfer. *Recommend activation.*
9. **Static-client write profile for Devcon** — direct-EOA prompt first; relayed profiles later. *Recommend yes.*
10. **Chain-id pin after freeze** — read-only on a fork unless posture B. *Recommend read-only.*
11. **Index replacement and plan invalidation** — every replacement voids unsent signed plans (testnet) or scoped invalidation later. *Recommend accept now.*
12. **State-only `publicationId → ordinal` lookup** — no map (this design). *Recommend no map.*
13. **Realm-origin preimage** — confirm. *Recommend confirm.*
14. **Paid complete listings** — accumulators in the closure. *Recommend accumulators.*
15. **First-milestone owner and implementer** — blocks S1 start. *Recommend: Claude implements `contracts-v2` under the 2026-10-13 mandate, with one named integration owner for the SDK/client vertical (the PM's ask, `AN/pm-requirements-release.md:227` item 6).*
16. **D-D narrowed** — presence families total; predicate families declared by Type authors in codec 2 as BITMAP families with per-scope coverage; K10 Etched; ROSTER reserved. *Recommend ratify.*
17. **Withdraw semantics** — occurrence-only. *Recommend occurrence-only for S1.*
18. **Testnet upgrade authority (the initialization plan's D5)** — EOA while data is disposable; a pinned Safe before data worth keeping. *Recommend as stated.*
19. **Stateful (`CALL`-mode) rules** — later. *Recommend later.*
20. **Record two one-line rulings** — the EAS exclusion and the frozen-dependency policy for Etched code (now mechanized as S16: every EFS code pin is scanned, dependency classes are disclosed, the terminal row carries `dependencyRoot`). *Recommend yes.*
21. **Acceptor gas as a floor (new)** — rules receive all available gas above the kernel tail, so a hostile Type in a signed plan can burn a relayer's whole `tx.gas` (bounded by the relayer's own limit and simulation) in exchange for Types that a repricing can never brick. Alternative: a Realm-level multiplier cap re-tunable by activation before freeze. *Recommend the floor.*
22. **Native lane bound by default (new)** — the SDK binds `expectedExecutionSet` and `expectedAcceptanceProfile` on every native call, so an activation or a policy activation between preparation and landing refuses the call (reprepare) instead of landing under changed rules. *Recommend bind by default; an explicit unbound option for apps that want "land anyway".*
23. **Permissionless `ReaderDirectory` (new)** — anyone may list a reader that names the ledger; the SDK trusts `release.json`, the directory is discovery only (readers can be fixed after freeze). Alternative: owner-listed, dead after freeze. *Recommend permissionless.*
24. **Freeze canary Type (new)** — `realm-notice/1` is registered at genesis and the freeze publishes a `frozen` record from the controller's principal. *Recommend yes.*
25. **Descriptor cap 4,096 B (new)** — the measured prototype cap; larger Types are a codec-2 question. *Recommend keep.*
26. **Non-atomic saves above the envelope (new)** — the SDK splits a save above the published maximum into several publications and labels it non-atomic (§12.2), while pm R3 (`AN/pm-requirements-release.md:138`) says a retry "never leaves half a save". Options: (a) accept the label and let the client surface a partially landed save as a visible state (each part keeps its own `AlreadyAdmitted` retry identity, so no part is ever duplicated); (b) stage-then-commit (kinds 8/9, b9) in a later kernel upgrade; (c) a smaller supported document. *Recommend (a) for M1 with the maximum published in `limits`, and (b) scheduled after S2.*
27. **Cost envelope and venue (new)** — a create-file is ≈ 1.5M today and ≈ 5.4M under EIP-8037 (§14, estimates), and no first public chain is named. *Recommend: name the first public testnet chain before S5, take the envelope from the C1 measurement on that chain's schedule, and plan against EIP-8037 pricing.*
28. **Registry self-report residual (new)** — a malicious registry implementation installed by activation can lie about `activeRevision()` until the freeze (risk 7; `AN/followup-6.md:360`, Q-J2). Options: accept until freeze (this design) or an immutable registry replaced by activation like the index. *Recommend accept until freeze; revisit only if a Safe-held upgrade key is retained after testnet.*
29. **Lens defaults and the seed principal (new)** — the PM asks to surface the empty-principal-list default and the multi-lens merge rule (`AN/SUMMARY.txt:317-319`); the fixture seeds the root under an EOA fixture principal (§13). *Recommend: at the contract readers an empty principal list means "no lens", never "all data"; the client supplies its defaults from `efs-deployment/1.defaultLensPrincipals`; first-touch-wins merge for M1; keep the EOA seed principal for testnets.*
30. **Devcon scope (new)** — whether Lists and a public home (M3) must be in the first testnet release (`AN/pm-requirements-release.md:227` item 7). *Recommend: Files plus the Solidity consumer for the first testnet; Lists and the home as S3 profiles.*
31. **Types as registry rows or as Records (new)** — `AN/critique.md` C-2. This design keeps the registry (rows, pins, its own proxy) and leaves Types-as-Records as a later profile convention over the registry id (§9.5(vi)). *Recommend rows now; a `TypeDescriptor/1` Record profile later if wanted.*
32. **Tags and the D-E budget (new)** — D-B and D-E (`OR:341-360`) rule one global concept id per folded string and a target of ≈ 50k gas per tag today (≈ 220k under Glamsterdam); a tag through the generic BIND path would cost ≈ 0.25M today and ≈ 1.2M under EIP-8037 (inferred from the §14 slot model: head, position, `bindingPosition`, admission row, plus history, role-scope, scope and backlink appends), roughly five times D-E. Tags are therefore outside C2 (§12.3) and designed in S3 against D-E — a dedicated tag family shape (for example a per-concept stance bitmap over principals rather than a binding per tag). *Recommend: hold tags to D-E and accept the S3 schedule; if D-E cannot be met, re-rule the budget explicitly rather than let the design widen it silently.*
33. **Freeze-trace waivers (new)** — which §16.7 rows may be waived for a given Realm's freeze. *Recommend: none for a persistent Realm; any for a throwaway rehearsal.*
34. **Build and backfill for later index families (new, from the build)** — §10.6 has the generation `DELEGATECALL` a pinned `IndexBuild`, but §2.2 S6 scans the generation as a plain runtime (no `DELEGATECALL`), and the activation check does exactly that today. Generation 1 declares no later family, so `build()`/`backfill()` revert and replay runs through a `STATICCALL`ed decoder plus the generation's own fold (no delegate). Options for the first generation that adds a family: (a) carry build/backfill in its own runtime and take the size on the cut ladder; (b) scan the generation with a `DELEGATECALL`-permitting table and pin the delegate. *Recommend (a); keep S6 whole.*
35. **(Closed 2026-11-24: the ledger computes its admin as the proxy's first creation; no set field.)** ~~Expected ProxyAdmin in the activation set~~ — step 5h checks `ProxyAdmin(adminSlot).owner() == controller` but the set names no expected admin, so a hostile implementation that rewrote the admin slot to a decoy owned by the controller would pass. Adding `expectedAdmin` to `ComponentSet` changes the execution-set preimage: a one-way door before the first persistent genesis. *Recommend add it now (one field, two words of code).*
36. **Freeze pre-check 8 scope (new)** — today it compares eleven of the seventeen limits; `maxTransitionBlocks`, `maxFreshSlotsPerPublication`, the floors and `kernelTail` are proven by the canaries instead. *Recommend compare all maxima and leave the floors to the canaries.*
37. **Replay tolerance rule (new)** — §10.6 lets a stricter later final hook skip publications admitted under a manifest without it. Generation 1's replay folds every publication on its recorded obligations and never re-judges. *Recommend keep "never re-judge" as the callback-profile law and drop the per-era rule (readers judge validity).*
38. **Native evidence rows store `acceptanceProfile = 0` (new)** — the facets re-derive `executionSet` and `indexObligations` from the revision row but not the acceptance profile (it needs the registry's policy and role history). Store it (one word per native publication) or keep deriving. *Recommend store it: one SSTORE, and recovery stays two calls.*

39. **Alias records in folders (new, from the build)** — `FilesFinalValidator` (generation 1) accepts only file subjects and directory records as FOLDER targets, so a `directory-alias/1` record cannot be placed in a folder, though the naming note wants aliases at old names. Allowing it is a validator change (a new unit, hence a new generation) or a reader-side convention. *Recommend decide before the first persistent Realm: allow alias records as FOLDER targets in the gen-1 validator now (one branch), since changing it later costs a generation.*
40. **A predicate's own `EXHAUSTED` reply (new, from the build)** — the wrapper treats a custom predicate's `EXHAUSTED` word as a refusal, so a hostile predicate cannot turn a refusal into "resubmit"; the cost is that a predicate which nests its own calls cannot report its own exhaustion (its caller sees `E_REJECTED`, class none). *Recommend keep the refusal: a predicate that needs nested calls declares a higher `validationGas` instead.*
41. **A CALL-only passthrough successor (new, from the build)** — §16.6 says migration to a "passthrough" successor is refused. The scan refuses a `DELEGATECALL` passthrough; a controller that merely forwards every call by `CALL` to another address is a plain runtime, so `migrate` accepts it when the set pins its codehash and discloses its `owner()`. No scan can tell forwarding from governance. *Recommend accept as disclosed: the execution set names the successor's codehash and owner, and `describe()` shows both; add the successor's code to the freeze rehearsal checklist instead.*
42. **(Closed 2026-11-24: activation refuses capabilities the build does not implement.)** ~~A lane that was enabled before its verifier exists~~ — a lane canary now has to be the lane it claims (a secp256k1 intent no longer satisfies the ERC-1271 slot), and freeze pre-check 7 forbids a terminal set from dropping a capability. So a Realm that enabled b2 while verifier profile 2 is still a stub cannot freeze until the profile ships. Options: (a) never enable a lane before its verifier exists (an operator rule; `activate` could refuse a capability whose profile is a stub), (b) let a terminal set drop a lane that never admitted a publication. *Recommend (a): `activate` refuses b2 until profile 2 lands, which is one check and keeps pre-check 7 whole.*
43. **(Closed 2026-11-24: the full rename is done under the PM's working default D5, the owner's rule being 'name everything as if v1 never existed'.)** ~~Protocol strings and "no v2"~~ — the protocol's identity strings carried the generation tag (`efs2/…` domains, `efs.<area>.v2.*` storage namespaces, EIP-712 version "2"); they are now `efs/…`, `efs.<area>.*` and version "1" (DESIGN.md adoption note 25).
44. **A cheaper carrier for on-chain bytes (new)** — a chunk stored as ledger storage words costs about 6.1M gas per 8 KB; v1 stored bytes as contract code (SSTORE2) for roughly a quarter of that today. A code-blob body carrier (capability b6, Q4) changes no record id and can be added by a kernel upgrade. *Recommend schedule it after the MVP if on-chain files larger than a few chunks matter before then; until then large files use external locations.*
45. **The 64-action ceiling (new)** — `limits.maxActions` is capped at 64 by the replay path; gas binds first on today's chains (about 20 edits or two 8 KB chunks per transaction). Lifting it needs chunked replay inside a publication. *Recommend keep 64 until a chain's gas limit makes it the binding constraint.*
46. **Where a `web3://` path starts (new; part of the directory discussion)** — the gateway serves `web3://<gateway>:<chain>/<principal>/<name>/…` and starts every walk at one root directory record fixed when the gateway is deployed (today the fixture's seed root, shared by every principal: `/alice/docs` and `/bob/docs` are two authors' views of the same root). Options: (a) keep one shared root per Realm, (b) a home directory per principal as the start, (c) put the starting directory in the URL. The choice is a gateway constructor argument or a path rule; a different answer is a new gateway deployment and no kernel change. *Recommend decide it with the directories-as-tags discussion; (a) stays until then.*
47. **The session lane (new; `docs/SESSION-LANE.md`)** — approve once, then write with no prompts while the user stays the author. Five rulings before S2 freezes the `Intent` typehash: S-1 who checks the session grant that the 2026-09-03 ruling already allows: the wallet (smart account, ERC-7715, ERC-1271; no kernel work, but not dependable for contract calls today) or the EFS kernel (a protocol session key; any wallet, the user stays the author); S-2 the meaning of the reserved `authorityId` and `authEpoch` fields; S-3 a nonce sequence per authority so two devices do not fight over one nonce; S-4 the default scope and the cap on session length; S-5 who pays for session writes (a funded session key, two prompts, or a relayer, one prompt). *Recommend the kernel for S-1, yes to S-2 and S-3, Files-only scope with a 24-hour default and a 30-day cap, and the funded key first; personas for the MVP until S2.*
48. **Media type lives in the content descriptor as a MIME string (new; built on the PM's working default, reversible before the first persistent deployment)** — every file's content descriptor now says what its bytes are, as a plain MIME string such as `image/png` or `text/html; charset=utf-8`, or nothing (unknown). Example: a photo saved as `holiday` with no extension is still served as `image/png`, and an author's `text/plain` note named `page.html` is served as text, never run as a page. The chain checks only that the string is lowercase and has no control bytes, so the `web3://` gateway can put it in an HTTP header safely and a client can compare it exactly; the SDK lowercases and checks it before it builds the plan, so a bad string never costs a failed transaction. Alternatives considered: (a) a property record per file: it costs a whole record plus a binding per file and is tied up with the held tag and property decisions; (b) a numeric code from a registry table: someone has to govern the table, and it cannot know next year's types (the same reasoning as the ruling that refused a URI scheme allowlist). Cost per file, measured: no media type costs nothing (a small on-chain file is 2.8k gas cheaper than before, an external one 0.1k dearer); `image/png` adds about 21k gas to a small on-chain file today (+0.8%; about 0.11M after Glamsterdam) and about 1.4k to an external one, whose locator usually leaves room in its last word; the 71-byte Word type adds about 72k (+2.8%). To change it James would say "store the media type as a property" or "use a fixed code list" before the first persistent Realm; after that the descriptor layout is a one-way door. *Recommend keep the MIME string in the descriptor.*
49. **A tag's number runs from −65,536 to 65,535 (new; built, docs/TAG-DESIGN.md §2)** — every tag carries a whole number: zero or above means "this applies" with that strength, below zero means "this does not apply". It rides in a field every bind already has (`Action.saltOrStrength`) and in 16 bits of the head row that were spare, so it costs nothing to store (a nonzero number costs about 12 gas more than zero). Example: Alice tags a photo `/nsfw` with 75 and Bob says −5 ("not this, mildly"); a reader can sort or threshold on those numbers. Alternatives: (a) a wider range, such as 32 bits: the head row has no more spare bits, so it costs a storage slot per tag with a nonzero number (about 22k gas today, 110k after Glamsterdam) and a layout change; (b) a sign only (yes/no): no saving, it just throws the strength away. To change it James would say "widen the number to N bits" before the first persistent Realm; after that the head row and the `Bound` event are one-way doors. *Recommend keep −65,536 to 65,535.*
50. **A tag can only be filed under a registered topic or an address's home (new; built, validator code 9)** — the profile validator refuses a first statement (either sign) under TAG whose place is neither a topic record (`topic-word/1` or `topic/1`) registered strictly before the statement, nor an address. Example: tagging a photo under `/cars/tesla` needs the two words and the path registered first (the SDK puts them in the same transaction, ahead of the tag); tagging it under a chess app's move record is refused. Alternatives: (a) accept any subject under TAG: an app's tag-like links would mix into the topic lists and readers, and a tag under an unregistered topic would silently miss its roll-up lists (the reason the "strictly before" rule exists); (b) a per-Type opt-in for "taggable places": a registry field and a validator branch, a new generation to change. Other apps get the same storage and the same lists from their own purpose at the same cost. To change it James would name the other place kinds he wants under TAG; it is a validator change, so a new index generation. *Recommend keep topics and homes only.*
51. **What a word may not be (new; built, `topic-word/1` codes)** — a word is 1 to 255 bytes of UTF-8 and may not contain `/`, `\`, ASCII control bytes, ASCII capitals or any Unicode white space; it may not be `.` or `..`, may not start with `~`, and may not be `0x` followed by 40 hex digits. Every word has its own root page, so the last two apply to every word of a path, not only the first. Example: `/tokens/usdc` is fine; `/tokens/0xa0b8…eb48` is refused because an address belongs in a tag as its target (tag the USDC contract under `/tokens/usdc`); `~efs` is refused because `~` paths belong to the system (`web3://…/~efs/o/…`); `tesla` followed by a no-break space is refused because it would only ever be a look-alike of `tesla` (every fold rule turns white space into `_`). Alternatives: (a) allow `~` words: they would collide with the gateway's system paths; (b) allow address-like words: a topic and a home would read the same in a link; (c) allow white space: two different topics would display identically. Each check costs 121 to 208 gas per byte of a new word, paid once at registration. To change it James would name the class to allow; the rule's code is part of the word Type's id, so the change is free only before the first persistent Realm. *Recommend keep all three refusals.*
52. **Everyone's versions of one file are not listed on chain (new; left to a later index generation)** — the index keeps every author's HEAD of a file in that author's own lists, and "what points at this" finds them by revision, but no list holds "every author who ever published a version of this file". Example: Alice creates `notes.md`, Bob saves his own version of it; Alice's lens shows hers, Bob's shows his, and a "show me everyone's versions" button needs an indexer or a later index generation. Price of keeping it now: a storage slot per file ever created, about 36k gas per file today and 124k after Glamsterdam, paid by every file whether anyone reads the list or not. Price of adding it later: a new index generation that builds the list from history before it is switched on (design §10.6); that build step is specified but not written, and writing and testing it is a pre-freeze gate (the build-from-history step must also reproduce three counters, design §10.6), so the deferral stays free only if that step lands before the Realm is frozen. To change it James would say "keep the all-authors HEAD list from genesis". *Recommend leave it to an indexer now and a later generation if it is wanted, with the build step written before any freeze.*
53. **The refused code point table is hand-written until one generator produces it (new; blocks the Topics Type ids)** — the word and text rules refuse a fixed table of Unicode code points (C1 controls, format characters, line and paragraph separators, joiners and variation selectors, white space beyond ASCII), written by hand from Unicode 15.1 into `TopicProfile.REFUSED`, copied into the JS vectors and into the SDK. The table is part of the rules' code, so it is part of the `topic-word/1`, `topic/1` and `text/1` Type ids: until one committed generator produces the Solidity constant, its JS copy and the SDK's vectors from one pinned Unicode version, those three ids are PROVISIONAL (tools/RELEASE.md). The generator waits on the fold-rule answer (which characters the SDK folds, and so which can never appear in a folded word). Example: if the fold rule maps ZWJ away, ZWJ stays refused; if it keeps emoji sequences intact, ZWJ must be admitted and the table changes, and with it the three Type ids. Alternatives: (a) ship the hand-written table as final: a later correction changes the Type ids and strands every topic registered under the old ones; (b) refuse less on chain and leave all of it to the SDK: a non-SDK writer could then register look-alike topics. To settle it James gives the fold rule; the generator follows, and the ids are final from then. *Recommend settle the fold rule and land the generator before any lasting deployment.*
54. **Sybil bumping in newest-first public views (new; measured, docs/TAG-NUMBERS.md "Spam rows")** — a place's public list puts every author's first yes about a thing at the front, so a newcomer's real tag shows as new; the price is that anyone can move a thing to the front of a public "newest first" view by saying yes to it from a fresh account. Example: someone wants their file at the top of the public `/memes` view and says yes to it from 64 new accounts in turn; each new account files one more entry for that thing. Measured price per bump: about 0.68M gas alone today (2.2M all gas after Glamsterdam), about 0.34M each when 64 are batched for one fresh account across 64 existing things (1.19M all gas after Glamsterdam); one account can bump a given thing only once, and the yes-count and distinct-item counts are not inflated beyond that one author. Lens views are not affected: they read only lens authors' lists. Alternatives: (a) file only the first statement by anyone: whoever speaks first fixes where a thing sits forever, so an early "not this" buries a later real tag (the reason for the 2026-11-25 amendment); (b) a cooling period or a fee per filing: needs a clock or value in the index, a kernel change. To change it James would choose (a) or say how much a bump should cost. *Recommend keep it as built, label public views as public, and show the lens count beside the global one.*
