# Questions for James — EFS core contracts

Product choices the design (`docs/DESIGN.md` §21) leaves to the founder, each with the engineer's recommendation. Engineering choices are **not** listed here: §20 of the design records them with the alternative rejected and why, and C1 measurements resolve the rest by pre-stated rules.

How these map to earlier question ids: the initialization plan's D1 (build identity = compiled bytes) is applied in the repository (`docs/BUILD-IDENTITY.md`); D2 (all Types described, permissionless) is the design's §9; D3a/D3b are the S4 import lane and the S2b ERC-1271 lane; D4 (branch protection) is a repository-settings item outside this list; D5 is Q18; D6 and the naming note's N1/N2 are Q7; N3 (alias-on-rename default) and N4 (`~efs` reservation) are client-side policy and the `files-name/2` rule respectively and stay open in the naming note.

**Before S1 starts:** Q15 (who implements and who owns the M1 integration). **Before the first persistent Realm (any lasting deployment):** Q1, Q2, Q13, Q18, Q22, Q39, Q48, Q49, Q50, Q51, Q52 and Q53 (Q52 and Q53 are ruled, 2026-11-26: the all-authors HEAD list is built in the list release, and the ASCII side of the word rule is built in the next release; the three Topics Type ids are final once the one generator of Q53 has produced the non-ASCII table). **Before S2 freezes the `Intent` typehash:** Q5, Q6. **Before S3:** Q16, Q32. **Before S5:** Q3, Q10, Q27, Q33. ## The questions (design §21)

6. **Declaration signature profile** — EIP-712 EOA declarations at launch; ERC-1271 creators later. *Recommend yes.*
7. **Names N1/N2** — `files-name/3` as the only Name Type; NFC and case policy in the client. *Recommend yes.* **Ruled 2026-11-26 in part:** "? # etc shouldn't be allowed as they are literally urlencode protected params. Nothing that breaks URLs.", and later the same day "Don't refuse windows reserved names. I only care about URI safety and us having some delimiters we can use for URL syntax". `files-name/3` (design §12.1.1) therefore refuses `#`, `?` and `%` (they change what a link means; `/` and `\` were refused already) and `<`, `>`, `"`, `|`, `:`, `*` and `;` (kept free as delimiters for EFS URL syntax, which is not designed yet), and, as the integration owner's application, a name ending in `.` (an auto-linker trims it). Windows device names such as `CON` or `nul.txt` are ordinary names. Example: `Q&A #3.pdf` and `a;b` are no longer file names; `Q&A 3.pdf` and `logo@2x.png` are. **Still open, before any lasting deployment:** two names that differ only by capitals or by Unicode normalization (`Report.txt` and `report.txt`, or `é` precomposed and decomposed) are two distinct names on chain, which stores names byte for byte.

47. **The session lane (new; `docs/SESSION-LANE.md`)** — approve once, then write with no prompts while the user stays the author. 48. **Media type lives in the content descriptor as a MIME string (new; built on the PM's working default, reversible before the first persistent deployment)** — every file's content descriptor now says what its bytes are, as a plain MIME string such as `image/png` or `text/html; charset=utf-8`, or nothing (unknown). Example: a photo saved as `holiday` with no extension is still served as `image/png`, and an author's `text/plain` note named `page.html` is served as text, never run as a page. The chain checks only that the string is lowercase and has no control bytes, so the `web3://` gateway can put it in an HTTP header safely and a client can compare it exactly; the SDK lowercases and checks it before it builds the plan, so a bad string never costs a failed transaction. Alternatives considered: (a) a property record per file: it costs a whole record plus a binding per file and is tied up with the held tag and property decisions; (b) a numeric code from a registry table: someone has to govern the table, and it cannot know next year's types (the same reasoning as the ruling that refused a URI scheme allowlist). Cost per file, measured: no media type costs nothing (a small on-chain file is 2.8k gas cheaper than before, an external one 0.1k dearer); `image/png` adds about 21k gas to a small on-chain file today (+0.8%; about 0.11M after Glamsterdam) and about 1.4k to an external one, whose locator usually leaves room in its last word; the 71-byte Word type adds about 72k (+2.8%). To change it James would say "store the media type as a property" or "use a fixed code list" before the first persistent Realm; after that the descriptor layout is a one-way door. *Recommend keep the MIME string in the descriptor.*
49. **A tag's number runs from −65,536 to 65,535 (new; built, docs/TAG-DESIGN.md §2)** — every tag carries a whole number: zero or above means "this applies" with that strength, below zero means "this does not apply". It rides in a field every bind already has (`Action.saltOrStrength`) and in 16 bits of the head row that were spare, so it costs nothing to store (a nonzero number costs about 12 gas more than zero). Example: Alice tags a photo `/nsfw` with 75 and Bob says −5 ("not this, mildly"); a reader can sort or threshold on those numbers. Alternatives: (a) a wider range, such as 32 bits: the head row has no more spare bits, so it costs a storage slot per tag with a nonzero number (about 22k gas today, 110k after Glamsterdam) and a layout change; (b) a sign only (yes/no): no saving, it just throws the strength away. To change it James would say "widen the number to N bits" before the first persistent Realm; after that the head row and the `Bound` event are one-way doors. *Recommend keep −65,536 to 65,535.*
50. **A tag can only be filed under a registered topic or an address's home (new; built, validator code 9)** — the profile validator refuses a first statement (either sign) under TAG whose place is neither a topic record (`topic-word/1` or `topic/1`) registered strictly before the statement, nor an address. Example: tagging a photo under `/cars/tesla` needs the two words and the path registered first (the SDK puts them in the same transaction, ahead of the tag); tagging it under a chess app's move record is refused. Alternatives: (a) accept any subject under TAG: an app's tag-like links would mix into the topic lists and readers, and a tag under an unregistered topic would silently miss its roll-up lists (the reason the "strictly before" rule exists); (b) a per-Type opt-in for "taggable places": a registry field and a validator branch, a new generation to change. Other apps get the same storage and the same lists from their own purpose at the same cost. To change it James would name the other place kinds he wants under TAG; it is a validator change, so a new index generation. *Recommend keep topics and homes only.*
51. **What a word may not be (new; built, `topic-word/1` codes; the ASCII part ruled 2026-11-26)** — a word is 1 to 255 bytes of UTF-8. Its ASCII is exactly `a`–`z`, `0`–`9`, `-`, `_` and `.` (James, 2026-11-26: "? # etc shouldn't be allowed as they are literally urlencode protected params. Nothing that breaks URLs.", and later "I only care about URI safety and us having some delimiters we can use for URL syntax"), so `c++`, `c#`, `r&b`, `~efs` and `Tesla` are not words; it may not end with `.` (so not `.` or `..`, nor `inc.`: an auto-linker trims it; the tag design session's proposal, not a ruling); it may not contain any Unicode white space; and it may not be `0x` followed by 40 hex digits (`0xsplits` is a word). Every word has its own root page, so these apply to every word of a path, not only the first. Example: `/tokens/usdc` is fine; `/tokens/0xa0b8…eb48` is refused because an address belongs in a tag as its target (tag the USDC contract under `/tokens/usdc`); `~efs` is refused because `~` paths belong to the system (`web3://…/~efs/o/…`); `tesla` followed by a no-break space is refused because it would only ever be a look-alike of `tesla` (every fold rule turns white space into `_`). Still open: the non-ASCII side (punctuation, symbols and separators outside ASCII, with the generator of Q53; the word Type id moves once more). Ruled since: a word may not start with `-` either (code 9, so `-word` stays free to mean "not" in link syntax: the tag design session's default applied by the integration owner, open to your veto; file names keep a leading `-`). Each check costs 121 to 208 gas per byte of a new word, paid once at registration. The rule's code is part of the word Type's id, so a change is free only before the first persistent Realm. *Recommend keep the address and white-space refusals.*

54. **Sybil bumping in newest-first public views (new; measured, docs/TAG-NUMBERS.md "Spam rows")** — a place's public list puts every author's first yes about a thing at the front, so a newcomer's real tag shows as new; the price is that anyone can move a thing to the front of a public "newest first" view by saying yes to it from a fresh account. Example: someone wants their file at the top of the public `/memes` view and says yes to it from 64 new accounts in turn; each new account files one more entry for that thing. Measured price per bump: about 0.68M gas alone today (2.2M all gas after Glamsterdam), about 0.34M each when 64 are batched for one fresh account across 64 existing things (1.19M all gas after Glamsterdam); one account can bump a given thing only once, and the yes-count and distinct-item counts are not inflated beyond that one author. Lens views are not affected: they read only lens authors' lists. Alternatives: (a) file only the first statement by anyone: whoever speaks first fixes where a thing sits forever, so an early "not this" buries a later real tag (the reason for the 2026-11-25 amendment); (b) a cooling period or a fee per filing: needs a clock or value in the index, a kernel change. To change it James would choose (a) or say how much a bump should cost. *Recommend keep it as built, label public views as public, and show the lens count beside the global one.*
